审批示例可以识别重试提交并返回原申请。本文说明键的持久保存、重试、升级和失败处理，不保证整个工作流或外部副作用恰好执行一次。本文的 schema 4/5 是引入提交键和类型化单据时的最低要求；当前完整版本范围见[存储与迁移](development/PERSISTENCE.md)。

<!-- topic:http-and-identity -->
## HTTP 与身份

独立端 `POST /api/requests` 和若依 `POST /arcflow/requests` 接受一个可选 `Idempotency-Key`。键须为 1–128 个 ASCII 字符，符合 `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`，精确比较且区分大小写。空值、格式错误、超长或多个值都会报错，不会忽略后继续创建。每次新提交生成密码学随机 UUID，重试保留原键。

作用域为 `(authenticated applicant ID, key)`。一个 JSON 文件对应一个配置流程；JDBC 同一数据库 schema 的所有流程共享键空间，不能按流程分别复用。身份来自宿主会话，JSON 不能指定。两名申请人可各自使用同键且不会泄露对方记录。重试仍要求申请人活动且拥有接口权限，返回保存结果前再次检查授权。这不是租户隔离；租户需另行授权的存储和身份接入。

<!-- topic:intent-and-replay -->
## 请求意图与重放

- 旧请假的意图包括配置流程 ID、流程版本、整数天数，以及按领域 `String.trim()` 规范化后的标题/原因。包括重试在内，先应用原始长度等校验，再规范化；Unicode 和大小写处理不变。
- 同一作用域键和相同意图返回原申请 ID、保存定义及**当前**状态/历史。后续审批可改变响应；重试不创建申请、不推进步骤，也不因新发布而换定义。
- 同键却更改规范化标题、原因、天数或流程版本，返回 HTTP 409，已有申请及映射不变。
- 已接受的提交可在流程重发、原审批人停用或新定义指派申请人后重试。这些限制针对新提交，不取消已接受申请；申请人仍须活动。
- 不带键时每次成功调用仍创建申请。旧 HTTP 正文、申请/事件形状与封装不变；独立端新建和重试均返回 201，若依保留 HTTP/AjaxResult 成功格式，无法只靠状态码识别重试。

带键 Java 调用为 `submit(actor, title, reason, days, processVersion, key)`；旧重载不带键。第三方 `ApprovalStore` 因默认方法仍可编译，但实现持久化支持前带键提交会明确失败，不回退到内存缓存。

## 原子性、竞争与失败

键映射、申请和首条 SUBMIT 审计一起保存。JSON 串行写入并原子替换一个文件。JDBC 先取得流程头锁，在检查活动版本**之前**查旧映射，再在同一事务插入三类记录；事务内重试还会锁定申请，防止并发决定造成返回申请与历史不一致。普通查找使用可重复读快照。同键并发创建只保存一笔申请，不同内容的竞争请求冲突。

即使响应丢失或连接清理失败，提交也可能已成功。保留**原键、原意图和原流程版本**重试，不能因未收到响应就换键，报错本身不能证明事务已回滚。键没有到期、淘汰、删除或复用机制，映射随保留的申请存在；宿主的保留、导入和恢复工具必须保留关联和作用域。

事务不包括业务表、通知、外部处理器或另一数据库，不提供 outbox 或 XA。JSON 仍要求本地文件系统中的一个进程，并受原有文件强制落盘与原子替换限制。测试覆盖重新打开进程或存储，不证明断电、设备故障、数据库物理重启/崩溃恢复；数据库持久性还取决于服务器配置与备份。

## 升级与回退

### JSON

此里程碑的流程定义保持 schema 2/3，快照 schema 4 新增 `submissions` 集合，申请/事件 JSON 不变。该阶段读取 schema 1–5，当前扩展读取 schema 1–13，见[迁移指南](development/PERSISTENCE.md)。读取不改文件。第一次成功的旧接口带键创建把 schema 1/2/3 升至 4，并把紧邻升级前的原始文件保存为 `*.schemaN.bak`，不覆盖已有备份。后续不带键写入和发布保持至少 4 并保留所有映射。类型化写入使用 5，之后旧接口写入也不降级。

重复或悬空映射、一笔申请绑定多个键、申请人不匹配会使恢复失败。不支持键的旧程序不能读 4，不支持类型化单据的程序不能读 5。升级前停流量并备份；回退不能用旧备份覆盖新接受申请。

### JDBC

提交键从 SQL revision 2 引入，与流程 JSON schema 独立。当前成员待办需要 SQL revision 3。新库使用对应方言的当前 `schema-*.sql`；revision 1 先执行一次 `upgrade-*-v1-to-v2.sql`，再显式执行 v2→v3 成员迁移与有界回填。停写、备份，并用获准账号迁移；旧申请不会凭空生成键。构造器不执行 DDL，即使客户端不带键也需要新表。MySQL 使用 InnoDB 与精确 `utf8mb4_0900_bin` 身份比较，见 [JDBC 宿主契约](../examples/approval-jdbc/README.md)。

全部宿主升级后再启用带键客户端。旧服务器可能忽略请求头而重复创建；不支持混跑或有流量时降级。

<!-- topic:client-retry-lifetime -->
## 客户端重试范围

独立与若依表单在当前表单和认证账号仍活动期间，将未确认提交的键、载荷及版本保留在内存。刷新服务端数据不改变未确认提交；修改规范化字段开启新意图，成功提交后清空。

只有明确的流程版本过期 HTTP 409 能证明尝试版本没有创建申请。收到该拒绝后，用户手动 Refresh 成功才清除失败尝试，让下次 Submit 使用新版本/新键；其他冲突或不确定失败不会自动换键。

表单不将申请文本或凭据写入浏览器存储。浏览器重载、关页或退出会丢失客户端键，应先检查申请列表再提交；服务端映射仍在。客户端不自动重试；仅供审批的移动端没有发起表单。

<!-- topic:verification -->
## 验证

测试覆盖规范化重放、改意图冲突、申请人隔离、精确大小写、非法键、相同/不同意图并发、校验前及创建过程中的获胜提交→发布竞争、当前状态重放、停用申请人/审批人、响应丢失、原子回滚、旧快照备份、损坏映射及重新打开存储。共享 JDBC 契约分别在 H2 和 CI 配置的真实 PostgreSQL/MySQL 上运行，真实服务器要求零跳过。HTTP/客户端测试验证两种封装与稳定重试键；应核对精确提交的工作流结果。

<!-- topic:typed-business-documents -->
## 类型化业务单据

`POST /api/documents` 和 `POST /arcflow/documents` 共用旧接口的申请人/键空间。重放比较流程 ID/版本、业务类型、业务 ID 与全部规范化不可变字段。跨旧请假/类型化请假、不同类型、不同流程或不同内容复用键均冲突。业务 ID 是引用，不是去重键。

不同 JDBC 流程锁不同头行，可争用同一全局键。只有映射 INSERT 明确重复、完整回滚后，才通过重新读取持久获胜记录协调；其他流程获胜会返回冲突，其他数据库/清理失败仍是错误。

旧接口带键 JSON 写入最低 4；首次类型化写入把 1–4 升到 5，逐字节保留旧备份，后续不降级。先部署兼容读取端再启用类型化写入，不混用写者。类型化单据沿用已有 SQL 载荷列；成员待办另需 SQL revision 3 显式迁移/回填。恢复旧 JSON 备份会丢失后续提交/审批，不是受支持的自动降级，见[业务兼容](BUSINESS_DOCUMENTS.md)。
